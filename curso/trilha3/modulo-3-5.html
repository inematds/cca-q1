📝 Exemplos Concretos vs Prosa

A forma mais eficaz de comunicar requisitos a Claude e atraves de exemplos concretos de entrada e saida (I/O), nao descricoes em prosa. Em vez de "formate como uma tabela com colunas alinhadas", mostre exatamente como a tabela deve ficar com dados reais. Exemplos eliminam ambiguidade de uma forma que palavras nao conseguem.

Essa tecnica e especialmente poderosa para formatos de saida, transformacoes de dados, regras de negocio complexas e convencoes de codigo. Um exemplo concreto comunica mais em 5 linhas do que um paragrafo de prosa em 50 palavras.

✅ Exemplo Concreto (eficaz)

Entrada: getUserById(123)

Saida: { id: 123, name: "Ana", role: "admin" }

Claro, inequivoco, reproduzivel

❌ Prosa (ambigua)

"Retorne um objeto JSON com os dados do usuario, incluindo identificador, nome e nivel de permissao."

Ambiguo: "nivel de permissao" e "role"? "level"? numero?

2

🧪 Iteracao Test-Driven

Na iteracao test-driven, voce escreve os testes ANTES de pedir a Claude para implementar. Os testes definem o contrato de forma executavel e inequivoca. Claude implementa ate que todos os testes passem. Se um teste falha, voce compartilha a saida e Claude corrige. O ciclo continua ate 100% green.

Isso e mais poderoso que qualquer descricao textual porque testes sao especificacoes executaveis. Nao ha ambiguidade: ou o teste passa ou nao. Claude recebe feedback preciso (assertion esperada vs recebida) e pode corrigir cirurgicamente.

💡 Ciclo TDD com Claude

1

Red: Escreva testes que definem o comportamento desejado

2

Green: Peca a Claude para implementar ate os testes passarem

3

Refine: Compartilhe falhas, Claude corrige, repita ate 100% green

3

🎤 Padrao Entrevista

No padrao entrevista, em vez de tentar especificar tudo de uma vez, voce pede a Claude para fazer perguntas antes de comecar. "Preciso implementar autenticacao. Antes de comecar, me faca perguntas sobre os requisitos." Claude identifica ambiguidades que voce nem percebeu e pede esclarecimentos.

Isso resulta em especificacoes mais completas e menos retrabalho. Claude pode perguntar: "JWT ou sessions? Refresh tokens? OAuth providers? Rate limiting?" — questoes que voce talvez esquecesse de especificar e que levariam a suposicoes erradas na implementacao.

🎯 Quando Usar o Padrao Entrevista

  • •Requisitos vagos ou incompletos — voce sabe o "o que" mas nao os detalhes
  • •Dominios complexos com muitas decisoes de design
  • •Features novas onde os trade-offs nao sao claros
  • •Quando voce quer evitar suposicoes incorretas de Claude
4

📐 2-3 Exemplos para Requisitos

O numero ideal de exemplos para definir um requisito ambiguo e 2-3. Um unico exemplo pode ser interpretado como caso particular. Dois exemplos revelam o padrao. Tres exemplos cobrem caso normal, edge case e caso de erro. Mais que tres raramente adiciona valor e consome tokens desnecessarios.

A estrategia e: primeiro exemplo mostra o caso feliz (happy path), segundo mostra um edge case (entrada vazia, valor limite, formato diferente), terceiro mostra tratamento de erro (input invalido, timeout, dados ausentes). Essa combinacao cobre a vasta maioria das situacoes.

📊 Estrategia dos 3 Exemplos

1

Happy path

Input normal, saida esperada padrao

2

Edge case

Input vazio, valor limite, formato alternativo

3

Caso de erro

Input invalido, como o erro deve ser tratado

5

🐛 Compartilhar Falhas de Teste

Quando testes falham, a saida do teste e o feedback mais preciso que voce pode dar a Claude. A saida contem exatamente qual assertion falhou, o valor esperado vs o recebido, a stack trace com o ponto exato de falha, e qualquer erro de runtime. Esses dados permitem diagnostico cirurgico.

Em vez de dizer "a funcao nao esta retornando o valor certo", compartilhe a saida completa do teste. Claude ve Expected: { id: 123 }, Received: { userId: 123 } e imediatamente identifica que o nome do campo esta errado. Isso economiza iteracoes e acelera drasticamente o ciclo de correcao.

💡 Principio: Dados Concretos > Prosa

A saida de um teste que falhou contem mais informacao util em 5 linhas do que um paragrafo inteiro de descricao verbal. Assertion + expected + received + stack trace = diagnostico preciso. Sempre prefira compartilhar a saida real.

6

🌍 Dominios Desconhecidos

Quando voce trabalha em um dominio onde nao tem expertise (Kubernetes, criptografia, otimizacao de queries SQL), as tecnicas de refinamento iterativo sao ainda mais valiosas. O padrao entrevista ajuda a explorar opcoes que voce nao conhece. Exemplos concretos validam que voce entendeu a solucao. Testes garantem que funciona mesmo sem voce entender todos os detalhes.

A combinacao ideal para dominios desconhecidos: (1) use o padrao entrevista para entender as opcoes, (2) peca a Claude para explicar trade-offs em linguagem simples, (3) defina exemplos concretos de I/O esperado, (4) escreva testes como rede de seguranca, (5) itere com feedback de testes ate convergir.

🎯 Dica para o Exame

O exame CCA testa cenarios onde o desenvolvedor nao e especialista no dominio. A resposta correta e sempre usar combinacao de tecnicas: entrevista para entender, exemplos para especificar, testes para validar. Nunca "confiar cegamente" na saida de Claude em dominios desconhecidos.

📋 Resumo Final

✓Exemplos concretos de I/O sao mais eficazes que descricoes em prosa
✓Iteracao test-driven cria um ciclo de feedback automatico e preciso
✓Padrao entrevista previne suposicoes incorretas em requisitos vagos
✓2-3 exemplos estrategicos cobrem happy path, edge case e erro
✓Saida de testes e o feedback mais preciso para Claude corrigir erros
✓Para dominios desconhecidos: combinar entrevista + exemplos + testes
