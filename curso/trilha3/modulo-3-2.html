🔧 Commands e Skills Customizados

Crie workflows reutilizaveis com commands de projeto e pessoais, e domine skills avancadas com SKILL.md, context: fork e allowed-tools para automacao segura.

1

📦 Commands de Projeto (.claude/commands/)

Commands de projeto sao arquivos Markdown em .claude/commands/ que definem workflows reutilizaveis para toda a equipe. Cada arquivo .md se torna um slash command invocavel por qualquer membro do time. Como estao no repositorio, sao versionados no Git e evoluem junto com o projeto.

O nome do arquivo define o nome do command: deploy.md vira /deploy, create-component.md vira /create-component. O conteudo do arquivo e o prompt que Claude recebe quando o command e invocado.

💡 Conceito Principal

Commands de projeto padronizam workflows da equipe. Um /review pode definir exatamente como fazer code review, um /test-component pode padronizar a criacao de testes. Todos usam o mesmo workflow, garantindo consistencia.

2

👤 Commands Pessoais

Commands pessoais ficam em ~/.claude/commands/ e estao disponiveis em TODOS os projetos, mas apenas para voce. Nao sao versionados no Git e nao sao compartilhados com a equipe. Sao ideais para automacoes pessoais de produtividade.

Exemplos de commands pessoais: /my-commit para formatar commits no seu estilo, /my-pr para criar PRs com seu template preferido, ou /explain para pedir explicacoes detalhadas no formato que voce prefere.

📦 Projeto (.claude/commands/)

  • •Versionado no Git
  • •Compartilhado com a equipe
  • •Especifico do projeto
  • •Workflows padronizados

👤 Pessoal (~/.claude/commands/)

  • •NAO versionado no Git
  • •Apenas para voce
  • •Disponivel em todos os projetos
  • •Preferencias individuais
3

⚡ Skills com SKILL.md

Skills sao uma evolucao dos commands que adicionam metadados via frontmatter YAML no arquivo SKILL.md. Enquanto commands sao simplesmente prompts em arquivos .md, skills podem definir configuracoes avancadas como modo de execucao, ferramentas permitidas e dicas de argumentos.

O frontmatter YAML fica no topo do arquivo entre delimitadores ---. Os campos mais importantes sao context (modo de execucao), allowed-tools (ferramentas permitidas) e argument-hint (dica de parametro). O restante do arquivo e o prompt da skill.

💡 Estrutura de um SKILL.md

O arquivo comeca com frontmatter YAML (entre ---), seguido pelo prompt em Markdown. O frontmatter define como a skill executa; o corpo define o que a skill faz. Essa separacao e fundamental para skills robustas.

4

🔀 context: fork

O campo context: fork no frontmatter de um SKILL.md faz a skill executar em uma sessao isolada — um "fork" da conversa principal. A skill tem sua propria janela de contexto, pode fazer operacoes verbosas sem poluir a conversa, e retorna apenas um resumo compacto ao contexto original.

Isso e essencial para skills que fazem muitas leituras de arquivo, buscas extensas ou exploracoes que consumiriam muitos tokens no contexto principal. O fork age como um subagente especializado que executa a tarefa e retorna o resultado filtrado.

🎯 Quando Usar Fork

  • •Skills que fazem buscas extensas em muitos arquivos
  • •Operacoes de analise que geram muita saida intermediaria
  • •Exploracoes de codebase que nao precisam ficar no historico
  • •Qualquer skill onde a jornada e menos importante que o destino
5

🔒 allowed-tools

O campo allowed-tools restringe quais ferramentas estao disponiveis durante a execucao de uma skill. E uma whitelist: apenas as ferramentas listadas podem ser usadas. Ferramentas nao listadas ficam completamente indisponiveis — Claude nem as ve como opcao.

Isso e um guardrail deterministico, nao probabilistico. Enquanto instrucoes no prompt ("nao edite arquivos") podem ser ignoradas pelo modelo, allowed-tools impede fisicamente o uso de ferramentas nao autorizadas. E a diferenca entre "pedir gentilmente" e "trancar a porta".

✅ allowed-tools (deterministico)

  • •Garante 100% que ferramentas restritas nao serao usadas
  • •Modelo nem ve as ferramentas nao listadas
  • •Auditavel e verificavel

❌ Instrucao no prompt (probabilistico)

  • •Modelo pode ignorar a instrucao em casos-limite
  • •Todas as ferramentas continuam disponiveis
  • •Nao-auditavel, depende do comportamento do modelo
6

💬 argument-hint

O campo argument-hint fornece uma dica visual sobre que tipo de argumento a skill espera. Quando o usuario digita o slash command, o argument-hint aparece como placeholder, guiando sobre o que passar como parametro.

Por exemplo, uma skill de review pode ter argument-hint: "caminho do arquivo ou PR", e uma skill de refactor pode ter argument-hint: "nome da funcao a refatorar". E uma melhoria de UX que torna skills mais descobriveis e faceis de usar sem consultar documentacao.

💡 Boas Skills sao Auto-documentadas

A combinacao de um bom nome de arquivo, argument-hint claro e corpo do SKILL.md descritivo cria skills que qualquer membro da equipe pode usar sem treinamento. O nome diz o que faz, o hint diz o que precisa, e o corpo define como faz.

📋 Resumo Final

✓Commands de projeto (.claude/commands/) sao versionados e compartilhados com a equipe
✓Commands pessoais (~/.claude/commands/) sao globais e privados
✓Skills usam SKILL.md com frontmatter YAML para configuracao avancada
✓context: fork executa em sessao isolada para operacoes verbosas
✓allowed-tools cria guardrails deterministicos por skill
✓argument-hint melhora a UX com dicas visuais de parametros
