🔗 tool_use + JSON Schemas = Saida Mais Confiavel

A combinacao de tool_use com JSON schemas e o metodo mais confiavel para obter saida estruturada de Claude. Em vez de pedir "retorne um JSON" no prompt (o que pode falhar com markdown, texto extra, ou formatacao inconsistente), voce define uma ferramenta cujo input_schema especifica exatamente a estrutura esperada.

Quando Claude "chama" essa ferramenta, os argumentos sao automaticamente formatados de acordo com o schema. O resultado e JSON valido, com os campos corretos e tipos esperados — sem necessidade de parsing manual ou limpeza de formatacao. Isso elimina uma classe inteira de bugs de integracao.

💡 Conceito Principal

Tool_use nao e apenas para chamar ferramentas externas — e o mecanismo padrao para saida estruturada. Defina uma ferramenta "ficticia" cujo unico proposito e forcar Claude a retornar dados no formato do schema. Os dados vem como argumentos da ferramenta, nao como texto livre.

📝 Exemplo: Ferramenta de Extracao

// Definicao da ferramenta

{"name": "extract_financial_data",

 "description": "Extrai dados financeiros do documento",

 "input_schema": {

  "type": "object",

  "properties": {

   "revenue": {"type": "number"},

   "net_income": {"type": ["number", "null"]},

   "currency": {"type": "string", "enum": ["USD","BRL","EUR"]}

  },

  "required": ["revenue", "currency"]

 }}

2

⚙️ Opcoes de tool_choice

O parametro tool_choice controla como Claude seleciona ferramentas. Existem tres opcoes principais, cada uma com casos de uso distintos. A escolha correta depende de se voce quer que Claude decida se precisa de uma ferramenta (auto), use alguma ferramenta obrigatoriamente (any), ou use uma ferramenta especifica (tool).

📍 As 3 Opcoes de tool_choice

1

tool_choice: "auto" (padrao)

Claude decide se quer usar uma ferramenta ou responder com texto. Ideal para agentes que precisam de autonomia de decisao.

2

tool_choice: "any"

Claude DEVE usar alguma ferramenta, mas pode escolher qual. Util quando voce tem multiplas ferramentas de saida e quer que Claude selecione a mais adequada.

3

tool_choice: {"type": "tool", "name": "X"} (recomendado para saida estruturada)

Forca Claude a usar a ferramenta especifica. Garante que toda chamada retorna dados no formato definido pelo schema. Ideal para pipelines de extracao.

3

⚠️ Schemas Eliminam Erros de Sintaxe, Nao Semanticos

Uma distincao critica: JSON schemas garantem correcao sintatica (formato valido, campos presentes, tipos corretos), mas NAO garantem correcao semantica (valores corretos). Um schema pode garantir que o campo "revenue" seja um numero, mas nao pode garantir que esse numero seja a receita correta extraida do documento.

Isso significa que schemas resolvem o problema de parsing (voce nunca recebe JSON malformado), mas voce ainda precisa de validacao semantica separada para verificar se os valores fazem sentido. Por exemplo, validar que a receita nao e negativa, que datas estao no range correto, ou que totais somam corretamente.

🚨 Armadilha Comum

Assumir que saida estruturada = saida correta e um erro perigoso. O schema garante que voce recebe {"revenue": number}, mas o valor pode ser 0 quando deveria ser 4.2M. Sempre implemente validacao semantica alem do schema.

✅ O que schemas resolvem

  • •JSON sempre valido e parseable
  • •Campos obrigatorios sempre presentes
  • •Tipos corretos (string, number, etc)
  • •Valores enum restritos a opcoes validas

❌ O que schemas NAO resolvem

  • •Valor correto no campo (semantica)
  • •Consistencia entre campos relacionados
  • •Dados fabricados vs extraidos
  • •Regras de negocio complexas
4

🔓 Campos Opcionais e Nullable para Dados Ausentes

O design do schema tem impacto direto na qualidade da extracao. Se todos os campos sao required e nao aceitam null, Claude e forcado a preencher cada campo — mesmo quando o dado nao existe no documento. Isso incentiva alucinacao: o modelo inventa um valor para satisfazer o schema.

A solucao e usar campos opcionais (fora do array "required") ou tipos nullable (usando "type": ["number", "null"]). Isso permite que Claude sinalize "este dado nao foi encontrado" retornando null, em vez de fabricar um valor. Combine com few-shot que demonstre o comportamento de retornar null.

💡 Design Defensivo de Schema

Marque como required apenas campos que SEMPRE existem no tipo de documento processado. Todos os outros campos devem ser opcionais ou nullable. Isso e especialmente importante em extracao de documentos nao padronizados onde campos podem estar ausentes.

📝 Schema Defensivo vs Rigido

Schema Rigido (forca alucinacao):

"required": ["revenue", "net_income", "employees", "founded_year"]

Schema Defensivo (permite nulls):

"required": ["revenue"]
"net_income": {"type": ["number", "null"]}

5

🎯 Forced Tool para Estrutura Garantida

Quando sua pipeline requer saida estruturada em 100% das chamadas, use tool_choice com o tipo "tool" e o nome da ferramenta especifica. Isso forca Claude a sempre "chamar" a ferramenta, garantindo que a saida seja no formato do schema. Claude nao pode decidir responder com texto livre em vez de dados estruturados.

O trade-off e que Claude perde a capacidade de dizer "nao consigo extrair esses dados" em texto livre. A solucao e incluir um campo como "extraction_status" no schema com opcoes como "success", "partial", "failed", permitindo que Claude sinalize problemas dentro do formato estruturado.

📊 Quando Usar Forced Tool

  • •Pipeline de extracao: Cada documento deve produzir exatamente um JSON com os campos definidos
  • •Classificacao em massa: Cada item deve receber exatamente uma classificacao estruturada
  • •Processamento downstream: O proximo passo da pipeline espera um formato fixo
6

📝 Descricoes de Campos no Schema

A propriedade "description" em cada campo do JSON schema funciona como instrucao embutida. Claude le essas descricoes e as usa para guiar a extracao. Uma descricao como "revenue_usd: receita total anual em dolares americanos, extrair da linha 'Total Revenue' do demonstrativo de resultados" e muito mais eficaz do que apenas "revenue_usd: number".

Descricoes ricas sao uma forma de engenharia de prompt que muitos desenvolvedores subestimam. Elas permitem especificar nao apenas o que extrair, mas de onde extrair, como formatar, e como lidar com ambiguidade — tudo dentro do schema que ja define a estrutura.

💡 Descricoes como Instrucoes

Descricoes de campos sao engenharia de prompt embutida no schema. Use-as para especificar: fonte do dado, formato esperado, unidade de medida, tratamento de ambiguidade, e valor padrao quando ausente. Quanto mais rica a descricao, mais precisa a extracao.

📝 Descricoes Ricas vs Pobres

Pobre:

"revenue": {"type": "number"}

Rica:

"revenue": {"type": ["number", "null"], "description": "Receita total anual em USD. Extrair da linha 'Total Revenue' ou 'Net Sales' do Income Statement. Se multiplos periodos, usar o mais recente. Retornar null se nao encontrado."}
