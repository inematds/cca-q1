📋 Hierarquia de CLAUDE.md

Compreenda os 3 niveis de configuracao do Claude Code — usuario, projeto e diretorio — e como usar @import e .claude/rules/ para organizar regras de forma eficiente e modular.

🏠 Nivel Usuario (~/.claude/CLAUDE.md)

O nivel usuario e o primeiro da hierarquia de configuracao do Claude Code. O arquivo ~/.claude/CLAUDE.md fica no diretorio home do usuario e e carregado automaticamente em TODAS as sessoes, independentemente de qual projeto voce esta trabalhando. Pense nele como suas "preferencias globais".

Este nivel e ideal para configuracoes pessoais que nao mudam entre projetos: seu estilo de comunicacao preferido, convencoes de commit que voce sempre usa, atalhos de produtividade, e preferencias de formatacao. Nao coloque regras especificas de projeto aqui — elas pertencem ao nivel projeto.

💡 Conceito Principal

~/.claude/CLAUDE.md e a configuracao global do usuario. E carregada em todas as sessoes, tem a menor precedencia na hierarquia (regras de projeto e diretorio sobrescrevem), e serve para preferencias pessoais universais.

🎯 Dica Pratica

Mantenha o CLAUDE.md de usuario enxuto. Cada token conta. Preferencias como "sempre responda em portugues" ou "use commits convencionais" sao bons candidatos. Documentacao extensa do projeto nao pertence aqui.

2

📁 Nivel Projeto (.claude/CLAUDE.md)

O nivel projeto e o mais importante na pratica. O arquivo .claude/CLAUDE.md na raiz do repositorio define as regras que todos os desenvolvedores do projeto devem seguir. E versionado no Git, compartilhado automaticamente com a equipe, e tem precedencia sobre o nivel usuario.

Aqui voce define convencoes de codigo do projeto, estrutura de pastas, dependencias importantes, padroes de arquitetura, e regras que Claude deve seguir ao trabalhar no projeto. Quando um novo desenvolvedor clona o repositorio, ele automaticamente recebe todas essas configuracoes.

✅ Colocar no Nivel Projeto

  • • Convencoes de codigo (TypeScript strict, ESLint rules)
  • • Estrutura de pastas e onde colocar novos arquivos
  • • Padroes de arquitetura do projeto
  • • Regras de testes e cobertura

❌ NAO Colocar no Nivel Projeto

  • • Preferencias pessoais de um unico desenvolvedor
  • • Documentacao extensa que deveria estar em docs/
  • • Segredos, credenciais ou tokens de API
  • • Base de conhecimento passiva sem instrucoes ativas
3

📂 Regras por Diretorio

Voce pode colocar arquivos CLAUDE.md em subdiretorios do projeto para definir regras especificas para aquela area. Quando Claude trabalha em arquivos de um diretorio que tem seu proprio CLAUDE.md, essas regras locais sao carregadas e tem precedencia sobre o CLAUDE.md da raiz do projeto.

Por exemplo, src/api/CLAUDE.md pode definir que todas as rotas devem seguir o padrao RESTful, usar validacao com Zod, e retornar erros no formato RFC 7807. Enquanto src/frontend/CLAUDE.md define regras de componentes React, uso de Tailwind e acessibilidade.

📊 Hierarquia de Precedencia

1

Mais alta: CLAUDE.md do subdiretorio

Regras locais mais proximas do arquivo sendo editado

2

Media: .claude/CLAUDE.md (projeto)

Regras do projeto na raiz do repositorio

3

Mais baixa: ~/.claude/CLAUDE.md (usuario)

Preferencias pessoais globais do usuario

4

🔗 @import Modular

A diretiva @import permite incluir outros arquivos Markdown dentro do CLAUDE.md. Em vez de um arquivo monolitico com centenas de linhas, voce pode modularizar suas regras em arquivos separados e importa-los conforme necessario.

Isso traz varias vantagens: manutencao mais facil (cada arquivo cuida de um topico), reutilizacao entre projetos (importar o mesmo arquivo de regras de seguranca em todos os repos), e organizacao clara (nomes de arquivo comunicam o proposito). E o padrao recomendado para projetos grandes.

💡 Como Funciona

No seu CLAUDE.md, use @import para incluir arquivos:

  • • O conteudo do arquivo importado e inserido no local do @import
  • • Caminhos relativos ao diretorio do CLAUDE.md que importa
  • • Permite reutilizacao de regras entre projetos via submódulos ou symlinks
5

📑 .claude/rules/ por Topico

O diretorio .claude/rules/ e a evolucao natural da modularizacao. Em vez de um unico CLAUDE.md com @imports, voce cria arquivos separados por topico: testing.md, api-design.md, security.md. O grande diferencial e que cada arquivo pode ter frontmatter YAML com o campo paths, controlando quando e carregado.

Isso significa que regras de testes so sao carregadas quando Claude trabalha com arquivos de teste, regras de API so quando trabalha com rotas, e regras de seguranca so quando trabalha com codigo sensivel. O resultado e um contexto muito mais enxuto e eficiente.

🎯 Dica para o Exame

O exame CCA testa extensivamente a diferenca entre .claude/rules/ com paths (carregamento condicional) e CLAUDE.md por diretorio (carregamento por localizacao). Regras com paths sao mais flexiveis porque podem cruzar diretorios e filtrar por tipo de arquivo, nao apenas por localizacao.

6

📝 Instrucao vs Base de Conhecimento

Uma distincao critica e entre instrucoes ativas e base de conhecimento passiva. O CLAUDE.md e para instrucoes — regras que Claude deve seguir ativamente. "Sempre use TypeScript strict", "nunca commite direto na main", "testes devem cobrir edge cases". Essas sao instrucoes claras e acionaveis.

Base de conhecimento, por outro lado, e informacao contextual: "O projeto usa PostgreSQL", "a arquitetura e microservicos", "o deploy e no AWS ECS". Essa informacao e util, mas nao e uma instrucao. Se voce preencher o CLAUDE.md com informacao passiva, ele fica inchado e as instrucoes reais se perdem no meio do ruido.

✅ Instrucao (CLAUDE.md)

  • • "Sempre use TypeScript strict mode"
  • • "Nunca use any — prefira unknown"
  • • "Testes devem usar describe/it, nao test()"
  • • "Erros de API devem seguir RFC 7807"

❌ Base de Conhecimento (NAO no CLAUDE.md)

  • • "O projeto usa PostgreSQL 15"
  • • "A arquitetura atual tem 12 microservicos"
  • • "Historico de decisoes arquiteturais..."
  • • "Lista completa de endpoints da API..."

📋 Resumo Final

✓ 3 niveis de configuracao: usuario (global), projeto (equipe) e diretorio (local)
✓ Precedencia: diretorio > projeto > usuario (mais proximo vence)
✓ @import permite modularizar regras em arquivos separados e reutilizaveis
✓ .claude/rules/ com frontmatter paths permite carregamento condicional por tipo de arquivo
✓ CLAUDE.md e para instrucoes ativas, nao base de conhecimento passiva
✓ Regras path-scoped economizam tokens carregando apenas o que e relevante
