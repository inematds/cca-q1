🌐 Servidores MCP no Claude Code

Configure e gerencie servidores MCP para estender Claude Code com ferramentas externas. Entenda configuracao por projeto vs usuario, variaveis de ambiente e resources.

📁 .mcp.json (Nivel Projeto)

O arquivo .mcp.json na raiz do projeto define servidores MCP especificos para aquele repositorio. Quando Claude Code abre o projeto, ele detecta e carrega automaticamente esses servidores, disponibilizando suas ferramentas. Como esta na raiz do projeto, e versionado no Git e compartilhado com toda a equipe.

Este e o padrao recomendado para ferramentas especificas do codebase — acesso a banco de dados do projeto, APIs internas, ferramentas de build, integracoes com o CI/CD do repositorio. Qualquer pessoa que clone o repositorio tera automaticamente as mesmas ferramentas MCP disponiveis.

💡 Conceito Principal

.mcp.json na raiz do projeto = ferramentas especificas do projeto, versionadas no Git, compartilhadas com a equipe. Carregamento automatico quando Claude Code abre o projeto. Ideal para integracao com banco de dados, APIs e ferramentas de build do repositorio.

⚡ Dica Pratica

Nunca coloque credenciais diretamente no .mcp.json. Use variaveis de ambiente (${TOKEN}) para secrets e documente no README quais variaveis precisam ser configuradas. O arquivo .mcp.json vai para o Git; credenciais nunca devem ir.

2

🏠 ~/.claude.json (Nivel Usuario)

O arquivo ~/.claude.json no diretorio home do usuario define servidores MCP pessoais, disponiveis em todos os projetos. E ideal para ferramentas que voce usa independentemente do projeto — integracao com Slack, email, calendario, ferramentas de produtividade pessoal.

Este arquivo NAO e versionado (esta no home do usuario, nao no repositorio). Cada membro da equipe pode ter suas proprias ferramentas pessoais sem afetar o projeto compartilhado. E a separacao correta entre configuracao pessoal e configuracao de projeto.

✅ ~/.claude.json (Usuario)

  • • Integracao pessoal com Slack, email, calendario
  • • Ferramentas de produtividade pessoal
  • • Disponivel em todos os projetos
  • • NAO versionado no Git

📁 .mcp.json (Projeto)

  • • Banco de dados, APIs internas do projeto
  • • Ferramentas de build e deploy
  • • Compartilhado com toda a equipe
  • • Versionado no Git
3

🔑 Variaveis de Ambiente

Servidores MCP frequentemente precisam de credenciais — tokens de API, senhas de banco de dados, chaves de acesso. A forma correta de fornecer essas credenciais e via variaveis de ambiente, referenciadas no .mcp.json com a sintaxe ${NOME_VAR}.

Por exemplo, um servidor MCP para GitHub pode referenciar ${GITHUB_TOKEN} no .mcp.json. O token real vem do ambiente de execucao — pode estar em um .env local, nas variaveis do CI/CD, ou no secret manager. A chave nunca aparece no repositorio.

⚠️ Alerta

Hardcodar tokens ou senhas no .mcp.json e um anti-padrao critico de seguranca. O arquivo e versionado no Git e visivel para toda a equipe. Sempre use ${VAR_NAME} para credenciais e documente quais variaveis precisam ser configuradas.

📊 Fluxo de Credenciais

  • • .mcp.json: referencia ${GITHUB_TOKEN} — vai para o Git.
  • • .env local: GITHUB_TOKEN=ghp_abc123 — NAO vai para o Git (.gitignore).
  • • CI/CD: variavel configurada no secret manager da plataforma.
  • • Runtime: expansao automatica de ${GITHUB_TOKEN} para o valor real.
4

📚 MCP Resources

Alem de ferramentas (tools), servidores MCP podem expor resources — catalogos de conteudo estatico ou semi-estatico. Resources incluem documentacao de API, schemas de banco de dados, guias de estilo, dados de referencia. Diferente de ferramentas, resources sao carregados automaticamente no contexto do modelo sem necessidade de chamada explicita.

A decisao entre expor algo como tool ou resource depende de se o conteudo e dinamico ou estatico. Se precisa de parametros e retorna dados diferentes a cada chamada (busca, consulta), e uma tool. Se e conteudo fixo que o modelo precisa ter disponivel (documentacao, schema), e um resource.

💡 Conceito Principal

Tools = conteudo dinamico, requer parametros, executado sob demanda. Resources = conteudo estatico/semi-estatico, carregado automaticamente no contexto, sem chamada explicita. Use resources para documentacao, schemas e dados de referencia; tools para buscas, consultas e acoes.

⚡ Dica Pratica

Exponha a documentacao da API do projeto como MCP resource. Isso permite que Claude Code tenha acesso automatico aos schemas e endpoints disponveis sem precisar buscar a documentacao manualmente a cada sessao.

5

🌍 Servidores da Comunidade

O ecossistema MCP inclui um catalogo crescente de servidores mantidos pela comunidade para integracoes comuns — GitHub, Slack, PostgreSQL, MongoDB, APIs REST genericas e muitos outros. Esses servidores sao testados, documentados e prontos para uso, eliminando a necessidade de implementar integracoes do zero.

O principio e claro: para integracoes padrao, use servidores da comunidade. Eles ja resolveram edge cases, tratam erros corretamente e sao mantidos por multiplos contribuidores. Criar um servidor customizado para GitHub quando existe um comunitario robusto e desperdicar tempo e adicionar risco desnecessario.

📊 Ecossistema de Servidores

  • • GitHub: issues, PRs, repositorios, code search.
  • • Bancos de dados: PostgreSQL, MySQL, MongoDB, SQLite.
  • • Comunicacao: Slack, email, notificacoes.
  • • Infraestrutura: Docker, Kubernetes, AWS, GCP.
6

🔧 Customizado vs Padrao

Servidores MCP customizados so devem ser criados quando nenhum servidor comunitario atende a necessidade. Tipicamente, isso acontece para APIs internas da empresa, workflows unicos do projeto, ou integracao com sistemas proprietarios. Para tudo que e padrao — GitHub, bancos de dados, Slack — use servidores comunitarios.

Criar servidores customizados desnecessariamente adiciona custo de manutencao, risco de bugs e complexidade operacional. Cada servidor customizado precisa ser mantido, testado e documentado pela equipe. Servidores comunitarios ja tem isso resolvido por multiplos contribuidores.

✅ Quando Customizar

  • • API interna da empresa sem equivalente publico
  • • Workflow unico que combina multiplas fontes
  • • Sistema proprietario sem integracao padrao
  • • Necessidade de logica de negocios especifica

❌ Quando NAO Customizar

  • • Integracao com GitHub, Slack, DBs populares
  • • "Quero mais controle" sem necessidade real
  • • Para aprender/praticar (use em projetos pessoais)
  • • Quando existe servidor comunitario funcional
