🚀 Claude Code em CI/CD

1

🖥️ Flag -p (Nao-interativo)

A flag -p (ou --prompt) e o ponto de entrada para usar Claude Code em pipelines CI/CD. Ela executa Claude em modo nao-interativo: recebe um prompt como argumento de linha de comando, executa a tarefa completa sem esperar input humano, e retorna a saida para stdout.

Sem a flag -p, Claude Code espera interacao do usuario via terminal — impossivel em um runner CI. Com -p, voce pode usar Claude Code como qualquer outro comando de CLI: claude -p "revise o codigo e sugira melhorias". A saida vai para stdout e pode ser capturada, parseada ou redirecionada.

💡 Conceito Principal

A flag -p transforma Claude Code de ferramenta interativa em componente de pipeline. E o requisito fundamental para qualquer integracao CI/CD: sem -p, nao ha automacao.

2

📊 --output-format json

A flag --output-format json faz Claude Code retornar a saida em formato JSON estruturado em vez de texto livre. Isso e essencial para automacao porque permite que scripts parseiem a saida programaticamente, extraiam campos especificos e tomem decisoes baseadas nos resultados.

Com output JSON, voce pode extrair informacoes como: arquivos modificados, resultado da tarefa (sucesso/falha), mensagens de erro detalhadas, e metricas. Sem JSON, voce dependeria de parsing de texto livre, que e fragil e propenso a quebrar quando Claude muda a forma como formata a resposta.

✅ --output-format json

  • •Saida estruturada e parseavel
  • •Integracao robusta com scripts
  • •Campos extraiveis programaticamente
  • •Nao quebra se Claude mudar formatacao

❌ Texto livre (sem flag)

  • •Parsing fragil com regex/grep
  • •Quebra quando formato muda
  • •Dificil extrair dados especificos
  • •Nao-confiavel para automacao
3

📄 CLAUDE.md no CI

No ambiente CI/CD, o runner clona o repositorio e executa Claude Code. O .claude/CLAUDE.md do projeto esta no repositorio, entao e carregado normalmente. Porem, o ~/.claude/CLAUDE.md (nivel usuario) NAO existe no runner CI — cada runner e uma maquina limpa.

Isso significa que qualquer configuracao necessaria para o CI deve estar no CLAUDE.md do projeto ou em .claude/rules/. Voce pode criar um arquivo especifico como .claude/rules/ci.md com regras para o ambiente CI: nao pedir confirmacao, ser mais conservador em mudancas, relatar erros em formato estruturado.

🎯 Dica Importante

Nao dependa de configuracoes de nivel usuario no CI. Tudo que Claude precisa saber para executar no pipeline deve estar no repositorio: .claude/CLAUDE.md e .claude/rules/. Teste localmente com um CLAUDE.md de usuario vazio para simular o ambiente CI.

4

🔍 Sessao Separada para Revisao

Uma pratica fundamental em pipelines CI/CD com Claude e usar sessoes SEPARADAS para implementacao e revisao. A sessao de implementacao gera o codigo; uma segunda sessao, completamente independente e com contexto limpo, revisa as mudancas geradas.

Na pratica, isso significa duas invocacoes separadas de claude -p: a primeira para implementar, a segunda para revisar. A sessao de revisao nao tem acesso ao raciocinio da sessao de implementacao, entao avalia o resultado objetivamente, sem o vies de "eu mesmo fiz isso".

📊 Pipeline com Sessoes Separadas

1

Sessao 1 — Implementacao: claude -p "implemente a feature X"

2

Testes automatizados: npm test (verificacao mecanica)

3

Sessao 2 — Revisao: claude -p "revise as mudancas do ultimo commit"

4

Decisao: Se tudo passa, criar/atualizar PR automaticamente

5

⚠️ Auto-revisao Enviesada

Auto-revisao enviesada e um anti-padrao critico que ocorre quando a MESMA sessao de Claude que implementou o codigo e usada para revisa-lo. O raciocinio que levou a implementacao ainda esta no contexto, criando um vies de confirmacao: Claude tende a avaliar positivamente decisoes que ele mesmo tomou.

Isso e analogo a pedir a um desenvolvedor para revisar seu proprio pull request — ele ja sabe por que tomou cada decisao e tende a justifica-las em vez de questiona-las. A mesma dinamica acontece com Claude: o contexto da sessao de implementacao "ancora" a avaliacao, reduzindo a capacidade critica.

🚨 Anti-padrao Critico

!

NAO faca: mesma sessao para implementar e revisar

O vies de confirmacao faz Claude avaliar positivamente seu proprio trabalho. Erros e problemas sao subestimados ou ignorados.

✓

FACA: sessao separada com contexto limpo

A sessao de revisao ve apenas o resultado (diff do codigo), nao o raciocinio. Avalia objetivamente, sem ancoragem no processo de implementacao.

6

🔧 Pipeline Pratico

Um pipeline pratico com Claude Code em CI/CD combina todas as tecnicas desta trilha. O fluxo tipico e: (1) receber trigger (issue, PR, schedule), (2) Claude implementa com -p, (3) testes automatizados rodam, (4) segunda sessao de Claude revisa, (5) se tudo passa, acao automatica (criar PR, comentar, merge).

Cada etapa usa --output-format json para parsing programatico. O CLAUDE.md do projeto configura o comportamento. Regras em .claude/rules/ podem ter configuracoes especificas para CI. E sessoes separadas garantem revisao nao-enviesada.

📍 Pipeline Completo

1

Trigger

Issue criada, PR aberto, schedule, ou webhook. Define o prompt para Claude.

2

Implementacao (Sessao 1)

claude -p "..." --output-format json — Claude implementa a tarefa.

3

Testes Automatizados

npm test, pytest, go test — verificacao mecanica das mudancas.

4

Revisao (Sessao 2)

claude -p "revise o diff..." --output-format json — sessao limpa revisa.

5

Acao Final

Se tudo passa: criar PR, comentar, ou merge automatico conforme configuracao.
